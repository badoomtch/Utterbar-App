# Utterbar 0.15.12 (beta)

Air-gapped activation, beta. Utterbar can now be activated on a machine that cannot reach utterbar.com, with the IT administrator handling the round-trip from a different machine.

This is a beta-only drop. Stable channel still serves v0.15.6.

## Air-gapped activation

If the machine running Utterbar cannot reach utterbar.com (lab kit, restricted network, classified environment, anything in between), the activation flow now has six honest steps and no network from the offline machine itself.

1. **On the offline machine**, open Settings, Licence, and click **Export activation request**. Utterbar writes a small JSON file (around 250 bytes) carrying the machine fingerprint, device name, app version, and an RFC 3339 timestamp.
2. **Transfer the JSON to your IT administrator**: email, USB stick, internal share, whatever your network policy allows. The file carries no licence material, only the machine's identity.
3. **The administrator signs in** to the admin panel at utterbar.com/admin, opens the licence detail page, and uses the new **Air-gapped activation** upload form. The server validates the format, counts the device against `max_devices`, and records an activation row marked offline.
4. **The administrator clicks Download licence.bin** on the same page. The file is the same 96-byte Ed25519-signed blob every other holder of this licence gets.
5. **Send the licence.bin back** to the offline machine via the same out-of-band channel.
6. **On the offline machine**, click **Import licence.bin** in Settings, Licence. Utterbar verifies the signature offline, copies the file to `%APPDATA%\Utterbar\licence.bin`, and asks you to restart. Restart Utterbar; the next launch picks up the file via the existing managed-licence loader.

Both buttons live on the existing Settings, Licence panel for users who are not yet activated. Pro and managed-fleet users do not see the air-gapped surface, since they already have a working licence by definition.

## What this release does not do

To set expectations clearly:

- **The licence.bin is not machine-bound in this version.** The file the administrator sends back is the same bytes for every device on the licence. A user who copies the file to a second offline machine could technically activate it there too. Treat the admin upload as audit and max-device intent, not as a cryptographic binding. A future v3 payload that embeds the fingerprint into the signed bytes is on the parking lot for buyers who need hard binding; mention it in your enquiry.
- **Offline devices do not heartbeat.** The activation row carries `last_heartbeat = null` permanently. The admin licence page renders a small Offline chip alongside such rows so the operator can tell at a glance which devices are reachable via heartbeat and which are not.
- **Revocation only takes effect on devices that contact the server.** If you revoke the licence in the admin panel, online devices flip to Free on their next heartbeat. Air-gapped devices that never contact the server keep running until you replace or remove their licence.bin on disk.
- **The request file itself is not signed.** Nothing in it is a secret; the fingerprint already leaks via the existing online activation path. The administrator's upload-validation step is the trust gate.
- **Re-uploading the same JSON for the same device is idempotent.** Useful when an admin is unsure whether the first upload landed.
