# Utterbar 0.13.1 (beta)

Hotfix for v0.13.0 — same Meeting Mode code, just packaged at a fresh version so the installer URL isn't behind a stale Cloudflare cache.

## Why this exists

v0.13.0 was published twice this evening — first with a broken migration sequence (the V3 slot collided with the v0.12.2-beta streaming-Zipformer migration), then with the fix. The second upload landed correctly in R2, but the CDN edge kept serving the cached body of the first upload from the same URL. Result: anyone who upgraded from v0.12.2-beta or installed the broken v0.13.0 hit a panic on launch (`applied migration V3__history_streaming is different than filesystem one V3__modes_meeting_mode`) and the "fix" download was identical to the broken one.

Bumping to 0.13.1 changes the installer URL (`releases/0.13.1/Utterbar-Setup-0.13.1.exe`), which the CDN has never seen before and therefore can't serve a stale copy of.

## What's in it

Identical to the intended v0.13.0:

- **Meeting Mode** — see [v0.13.0 release notes](0.13.0.md) for the full description
- The corrected V0003/V0004 migration sequence

## Operator note (for future me)

When republishing a release after a bad ship:

1. The R2 PUT is fine, but Cloudflare can serve stale cached bodies from the same URL even with `cf-cache-status: DYNAMIC` headers — don't trust the in-band cache headers.
2. The two reliable fixes: bump the version (changes the URL) or purge the Cloudflare cache via the API. The version bump is faster and needs no extra credentials.
3. Don't reuse a migration version slot across a revert — a beta-shipped V-number is consumed forever.
