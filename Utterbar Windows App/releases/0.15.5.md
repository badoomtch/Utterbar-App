# Utterbar 0.15.5 (beta)

Phase A of the GPU-acceleration work. Provider truthfulness, observable telemetry, no behaviour change to your transcripts. DirectML itself is still v0.15.6.

## What this fixes

Settings → Advanced has had a "GPU acceleration" card since v0.6 with three options: Auto, DirectML, CUDA. The card claimed running on the GPU was "3–10× faster than CPU". In reality the shipping ONNX Runtime in this build is CPU-only — the DirectML satellite DLLs (`onnxruntime_providers_dml.dll`, `DirectML.dll`) have never been bundled. A user who picked DirectML still ran on CPU; the UI didn't say so; logs didn't say so.

v0.15.5 makes the gap visible. It does not close the gap — that's v0.15.6.

## What v0.15.5 changes

- **Settings → Advanced → GPU acceleration is honest.** The card description now says *"This build runs on CPU only. DirectML and CUDA appear here so your preference is preserved for a future release that ships GPU support, but they have no effect today."* The "3–10× faster" copy is preserved in the source and gated behind a runtime-capabilities check, so it'll fire automatically when v0.15.6 lands.
- **Inactive notice on DML/CUDA rows when selected.** If you have DirectML or CUDA selected, the row shows: *"Selected, but currently inactive — this build does not include that execution provider. Transcribes are running on CPU."* Your preference is preserved across the upgrade so v0.15.6 picks it up automatically.
- **Provider telemetry on every transcribe.** The meeting and dictation log lines now carry `provider_requested`, `provider_used`, `fallback_used`, `fallback_reason`. Run a meeting on Small with DirectML selected and the log records:
  ```
  provider_requested="directml" provider_used="cpu" fallback_used=true fallback_reason="dml_ep_unavailable"
  ```
  Same with Auto + hardware GPU detected: `provider_requested="auto-cpu"`, no fallback (Auto picks the path that was going to work; it doesn't call CPU a downgrade).
- **Provider downgrade is real, not just a log claim.** When DirectML or CUDA is requested but the runtime can't serve it, the engine actually receives `"cpu"` as its provider string. v0.15.4 logged `provider_used="cpu"` while passing `"directml"` to sherpa-onnx — that was false telemetry; v0.15.5 fixes it.
- **Runtime-capability probe.** A new `runtime_capabilities` IPC command does a file-presence check next to the running executable. Cheap, deterministic, easy to read. Today both `has_dml_ep` and `has_cuda_ep` are `false` against the shipping runtime; v0.15.6 will flip them when the new DLLs land.

## What this does NOT change

- Your transcripts. Same audio in, same text out as v0.15.4. No engine-layer changes to Whisper or Parakeet.
- Meeting Mode default (still Whisper Small from v0.15.4).
- The Meeting Mode allow-list (still Small / Medium / Large v3 only).
- The `gpu_acceleration` setting itself. If you had DirectML selected, you still have DirectML selected — the inactive notice explains why your transcribes aren't running on it.
- `is_whisper_hallucination` (the `[Music]` / "Thanks for watching" filter from v0.8.8) — unchanged.

## Logs

Tail `%APPDATA%\Utterbar\logs\utterbar.log.*` for `meeting transcribe complete` or `inference.transcribe done` to see the new fields. Useful for diagnosing performance and provider behaviour without needing the app's UI.

## Why split DirectML across two releases

v0.15.5 lands the observability — the easy, low-risk half. v0.15.6 is the actual DirectML runtime work: swapping the vendored `runtime/` DLL set, building sherpa-onnx from source with the `directml` feature, validating against all four model engines, adding a CPU fallback path that handles native crashes with sentinel-file detection. That's a multi-day infra change with real risk; doing it cleanly meant separating it from the user-visible truthfulness fix.

The result of v0.15.5: nothing about your transcribes changes, but you now have honest UI copy and telemetry to read. The result of v0.15.6: GPU acceleration actually runs.

## Beta only

Beta-channel release. No `--announce`, no `latest` tag. Stable channel still serves v0.12.0.
