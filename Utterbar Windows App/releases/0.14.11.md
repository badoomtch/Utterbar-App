# Utterbar 0.14.11 (beta)

Restores the audio capture path that worked through v0.14.6. Beta channel.

## Why

v0.14.7 → v0.14.10 chased a "tinny mic" report by changing the capture path:
forced 48 kHz, restricted sample formats, then swapped the resampler for an
FFT-based one (rubato `FftFixedIn`). Two real problems came out of that
sequence:

1. **Hotkey-to-listening latency went from 7-20 ms to 394-449 ms.** The FFT
   resampler precomputes its plans inside `start_recording`, on the same
   thread the hotkey is waiting on. Pre-v0.14.7 there was no such precompute.
2. **Transcript accuracy regressed.** Test phrases came back as fragments —
   "Is this working now" → "This point.", "I feel like this is way worse of
   an app now" → "I feel it's way worse than out though." The chunked FFT
   resampler dropped tail samples (anything below a full input window at
   end-of-recording was silently discarded), and the choice of FFT over the
   simple linear interpolator wasn't fixing a real problem on Jay's hardware
   in the first place — the linear path had been working since the early
   versions.

## What changed

- `services/audio/capture.rs` is restored to the v0.14.6 baseline (commit
  `b88ba50`). The picker accepts the device's `default_input_config()`
  directly and the resampler is the in-line linear interpolator that has
  been in production since the early versions.
- `services/audio/resample.rs` (the FFT resampler module added in v0.14.9)
  is removed entirely. `rubato` stays in `Cargo.toml` for now — it's a small
  dep and a properly-engineered resampler is on the v0.15 list.
- New stage timings on the capture path so the next "feels slow" report can
  be diagnosed from a single log line:
  - `audio capture stream opened` carries `device_name`, `sample_format`,
    `src_rate`, `channels`, `cfg_ms` (time spent in `default_input_config`).
  - `audio capture stream armed` carries `build_ms` (build_input_stream)
    and `play_ms` (stream.play).
  - `start_capture returned` (DEBUG) carries `mic_arm_ms` so the dictation
    layer can see how long the audio service took.
  - The existing `audio capture armed` line at the bottom of
    `start_recording` keeps its `elapsed_ms` field for the end-to-end view.
- New diagnostic mode: `audio.diagnostic_audio_dump` (default off). When
  on, every recording writes `<ulid>-raw.wav` and `<ulid>-processed.wav`
  to `%APPDATA%\Utterbar\diagnostics\audio\` — the raw post-capture PCM
  and the exact PCM handed to the ASR. Self-rotating: keeps the latest 6
  pairs (12 files). Off by default because it's private audio on disk;
  flip it on in `settings.json` only when reproducing a quality bug.
- Regression tests pinning the linear resampler's behaviour
  (48 k → 16 k duration preservation, 16 k pass-through, no amplitude
  collapse on a speech-level tone) and pinning the preprocess passes
  (`Off` is a true no-op, `Aggressive` doesn't gate speech to silence,
  `noise_gate` doesn't kill continuous tone, `normalise` doesn't drop
  the peak).

## What this fixes

- Hotkey-to-listening latency is back near pre-v0.14.7 baseline (a few ms).
- The audio handed to Parakeet is the same audio that was working in v0.14.6.

## What this does NOT change

- Preprocessing defaults — already correct (everything off except optional
  `dynamic_normalisation`). Nothing in the preprocess path was the cause.
- The FFT resampler is left as a follow-up. If a real "tinny audio"
  reproduction lands in v0.15 we'll port a properly-engineered version off
  the start_recording critical path (built once at app boot, lazy-init in
  callback, with tail-flushed `finish()` wired in).
