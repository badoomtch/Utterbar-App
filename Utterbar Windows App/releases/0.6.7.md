# Utterbar 0.6.7

**The crash-fix + product-polish release.** The heap-corruption / illegal-instruction crash that has been dogging every build since v0.6.2 is resolved at the source — a two-line patch to a vendored copy of Tauri's runtime crate (`tauri-runtime-wry 2.10.1`). Plus four targeted UX improvements. Everything that was already fixed in v0.6.6's working tree carries forward.

If you've been experiencing random crashes during dictation or while the app is idle — those should now be gone. If you see a new crash, please send the minidump from `%APPDATA%\Utterbar\logs\`: v0.6.6's expanded logging + v0.6.7's matched PDB will let us diagnose any new issue precisely.

## New — UX polish

- **Cold-load status.** The first dictation after launch (or after the idle sweeper has unloaded the model) takes 5-12 seconds for the ASR engine to start. Previously the bar showed "Processing" throughout, which read as the app hanging. The bar now shows "Initialising model" in an accent tone directly from the moment the recording stops — no flash of "Processing" first — and then transitions to "Processing" only once the model is loaded and the actual inference is running. Subsequent dictations against a warm model go straight to "Processing" as before.
- **Floating bar closes in one motion.** The expand→collapse animation previously looked like two sequential shrinks because the inner content wrapper remained mounted during its 280ms opacity fade-out, contributing width to the outer `layout` animation, which then snapped again when the child finally unmounted. The inner wrapper is now always mounted with `max-width: 0` driven state instead of `AnimatePresence`, so the outer pill and the inner content collapse along the same timeline. One motion, no stepped shrink.
- **Search and sort for custom words.** The vocabulary list now surfaces a search box + A–Z / Recent sort toggle once you have 10 or more entries. Replacements get a search box on the same threshold. Row density is tighter so more of a long list fits on-screen. Keeps the workflow fast for small lists (the controls don't appear until you need them) while making a 50+ entry list genuinely usable.
- **Floating bar remembers its last position.** After any drag, the bar's position is saved to `%APPDATA%\Utterbar\config\floating_position.json`. On next launch the bar reopens at exactly where you left it — no snapping back to top-centre. Validation happens against each monitor's taskbar-aware work area, and a pre-show clamp runs unconditionally, so the bar is never painted behind the taskbar or off-screen on first frame. If the saved position is no longer valid (monitor unplugged, resolution changed and the coords would now be off-screen or inside the taskbar strip), the bar falls back to the default position and then clamps into the visible work area. The tray's "Reset position" option clears the saved file so you always have an escape hatch.

## Fixed — the crash

**What was happening.** Every IPC message from the floating bar or main window to the Rust backend triggered an internal `Context::clone` deep inside Tauri's runtime. That clone walked a non-atomic reference-counted pointer (`Rc<EventLoopRunner>`) which — when the clone happened on a background worker thread rather than the main UI thread — either corrupted the Windows heap (caught later as `STATUS_HEAP_CORRUPTION`) or tripped Rust's built-in thread-safety assertion (`ILLEGAL_INSTRUCTION`). Four minidumps across v0.6.4–v0.6.6 all bottomed out at the same Rc operation.

**What was fixed.** Utterbar now vendors `tauri-runtime-wry` locally (at `src-tauri/vendor/tauri-runtime-wry-2.10.1/`) with a targeted two-line patch. The offending field is now wrapped in an atomic reference-counted pointer (`Arc`) so the per-IPC clone is thread-safe without touching any of the runtime's inherently single-threaded internals. Not a blanket `Rc → Arc` change — the specific field that was being cloned on the wrong thread is the only thing that changes.

**Upstream.** The underlying bug is tracked at [tauri#10001](https://github.com/tauri-apps/tauri/issues/10001) (open, no fix in progress). Tauri's own source code already self-documents the pattern for a sibling field: `// changing this to an Rc will cause frequent app crashes.` — we extend that fix to the outer wrapper. When/if Tauri accepts an upstream PR, we'll drop the vendored directory and track the official version.

## Fixed — UX

- **Licence persists across restarts.** The licence cache now writes to both Windows Credential Manager and a fallback file under `%APPDATA%\Utterbar\`. On launch we read whichever is populated first. Previously the keyring save occasionally returned success without actually persisting, leaving the app back on Free after the next launch.
- **"No audio detected" when the clip was silent.** Previously, if you tapped the hotkey by accident or said nothing, the bar still reported "Inserted" and wrote a history row. Now it surfaces "No audio detected", skips the paste, and doesn't pollute history.
- **British mode no longer turns every "check" into "cheque".** The financial-instrument sense and the verb sense are indistinguishable in text, so a deterministic swap could only be wrong. We kept every other deterministic swap — `colour`/`color`, `organise`/`organize`, `favourite`/`favorite`, etc. — and removed just the one rule that was causing noise.
- **Recording indicator dot no longer clipped** by the pill's edge during an active dictation.
- **Floating bar border stays lit cyan for the whole drag.** Reimplemented as a pure CSS rule on a DOM attribute written synchronously at pointer-down. Previous attempts drove the border via React state, which never repainted during the native window-move loop because WebView2's renderer doesn't generate frames while Windows owns the drag. The new approach doesn't need a React re-render — the compositor paints on the next cycle from the attribute change alone.
- **App version shown beneath the "About" item in the left sidebar.** In addition to the existing footer strap and the About page itself.

## Fixed — recording reliability

- **Stuck-hotkey recovery.** If the frontend's phase store somehow desyncs from Rust (e.g. a dropped event), a hotkey press that would previously have been silently rejected now:
  1. runs a recovery `stop_recording` on the Rust side to clear the live capture,
  2. forces the local phase store back to Idle,
  3. logs the incident to both the Rust log and the devtools console.

  The next press starts cleanly. Previously the only way out was to quit and relaunch the app.

- **Rust-side resync on reject.** When `start_recording` rejects because a capture is genuinely still in flight, it now re-emits a fresh `Listening` phase event. That nudges the frontend store back into the correct state so the user's next hotkey press decides correctly between start and stop.

## Changed — modes

We reduced the "I changed a mode setting and it silently didn't do anything" foot-guns by making global settings authoritative where they used to be silently overridden by mode-level duplicates.

- **Per-mode ASR model picker removed** from the Mode Editor. Previously this shadowed the global Models setting — you could pick a model per mode, but the interaction with "default ASR model" was confusing. Now the global setting wins and the per-mode picker is gone. The field stays in the persisted mode struct for back-compatibility with existing mode rows on disk; it's just no longer read or editable.
- **Per-mode Context Rules block removed** from the Mode Editor. Same pattern — mode-level `use_clipboard`/`use_selection`/`use_active_app` were ANDed with the global Privacy toggles, which meant flipping a mode toggle silently did nothing if the global was off. Now Privacy alone controls what context is captured.

If you want a specific model or context rule for a specific mode, that's a feature request for a future release — this change aligns the settings with how they actually behaved in practice.

## Diagnostics

Added structured logging for the state machine so future bug reports can be diagnosed from logs alone:

- Phase transitions are logged on every `set_phase` call (idle / warming / listening / processing / success / error / cancelled / no_audio).
- The flag state for `recording_in_progress` and `transcribe_in_progress` is logged on every `start_recording` and `stop_recording` entry.
- Dropped `emit` calls (which used to be silently swallowed) now log at error level.
- The frontend console prints every phase event received and the decision the hotkey handler made, so a devtools log captures the full start/stop lifecycle.
- The crash analyser script at `scripts/analyse-crash.ps1` was rewritten to actually parse and run cleanly. Previous versions had a string-quoting bug that broke path resolution on paths with spaces.

## If you see any new crash

The crash pattern fixed in this release is a very specific one (two very specific stack shapes across four minidumps). If you hit something different in v0.6.7, we'll want to know:

1. The minidump at `%APPDATA%\Utterbar\logs\crash-*.dmp` (the SEH handler writes these automatically).
2. The tail of `%APPDATA%\Utterbar\logs\utterbar.log.<today>`.
3. Run `scripts\analyse-crash.ps1` from a PowerShell prompt in the app directory — prints a symbolicated stack of the crashing thread.

v0.6.7 carries forward v0.6.6's expanded logging, so most new issues should be traceable from the log alone.
