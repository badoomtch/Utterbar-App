# Utterbar 0.14.10 (beta)

Hotkey-to-listening latency back to pre-v0.14.7 levels. Beta channel.

## What changed

In v0.14.7 onwards the picker called `device.supported_input_configs()` on every start_recording. On Windows that's a slow API — WASAPI iterates every `(rate, format, channels)` combo the device exposes — so it added 100-300 ms of latency between pressing the hotkey and the bar showing the listening state. Pre-v0.14.7 we used only `default_input_config()` which is a single, fast call.

v0.14.10 takes a fast path: if `default_input_config()` already returns a format we can decode (F32 / I16 / U16), use it directly without enumerating. The slow enumeration only runs when the default's format is one of the rare uncomfortable ones (U8, I8, I32) and we need to find a sibling config with a decodable format. On every common consumer mic and pro interface, the fast path applies and the start_recording overhead is back to pre-v0.14.7 levels.

The FFT resampler from v0.14.9 stays exactly as it is — it isn't on the critical path between hotkey and listening, it runs inside the cpal callback closure after the stream is already armed.

The "audio capture armed" log line now includes `elapsed_ms`, so future "is this still feeling slow?" diagnoses can read the wall-clock latency from the log rather than diffing timestamps.

## If something does go wrong

`%APPDATA%\Utterbar\logs\` has the app log. The new `elapsed_ms` value on the "audio capture armed" line is the time from `start_recording enter` to "you can speak now". On a healthy system that should be 100-200 ms; if it's 500+ ms, send the log slice.
