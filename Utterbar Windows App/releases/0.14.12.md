# Utterbar 0.14.12 (beta)

Selected microphone is actually used. Beta channel.

## Why

Pre-fix, the floating bar / hotkey / tray-start paths invoked
`start_recording` with `deviceId: null`, and Rust treated `null` as "use
the Windows default input device" — so the Audio settings dropdown only
took effect if you launched recording from the Onboarding flow (which
had a separate code path that passed the selected device).

Reproduced 2026-04-28: Focusrite USB selected in Audio settings, but
every recording was captured by the Intel Smart Sound array mic, with
the array's aggressive on-device DSP munging the audio before it ever
reached Parakeet. Setting the Focusrite as the **Windows** default
made it work; choosing it in Utterbar settings did nothing.

## What changed

### 1. Device resolution moved into Rust

`dictation::start_recording` now reads `settings.audio.input_device_id`
when the caller passes `null`. The contract is "`null` means use the
configured device, falling back to the host default if the user hasn't
configured one." All four front-end entry points (floating bar,
onboarding, AppBootstrap recovery, tray menu) keep passing `null` and
get the right behaviour automatically.

### 2. Visible warning when the configured device isn't available

If the configured device isn't found (USB mic unplugged, renamed in
Sound settings, audio service restarting), Utterbar still falls back
to the host default — but a `dictation:error` event fires with a
clear message: *"Selected microphone 'X' isn't available — recording
with 'Y' instead. Plug the device back in or pick another one in
Audio settings."* That feeds the existing OS notification surface
(`design/notifications.ts`), so the user sees a Windows toast instead
of silently recording from the wrong mic.

### 3. Structured logging on every recording

Every `start_recording` now writes a single info line that names the
requested vs configured vs effective device id:

```
start_recording: resolving input device
  requested_device_id=None
  configured_device_id=Some("Analogue 1 + 2 (2- Focusrite USB Audio)")
  effective_device_id=Some("Analogue 1 + 2 (2- Focusrite USB Audio)")
```

Followed by `start_capture returned` carrying `resolved_device_name` —
the canonical "what mic actually recorded you" answer. On a fallback
the existing `WARN` line carries `reason` (NotFound / EnumerationFailed)
and the resolved fallback name, so future "wrong mic" reports are
diagnosable from one log slice.

### 4. Cpal device matching is now a pure function with tests

`match_input_device(requested, &[(id, name)]) -> DeviceMatch` covers:
- `None` → `Default` (use host default)
- exact name match → `ExactByName { index }`
- duplicate names (Windows ships some USB mics this way) → first
  match plus a `total_matching` count for diagnostic logging
- not found → `FallbackNotFound`

Five unit tests pin the rules — including one for the duplicate-names
case which previously had no coverage.

## What this fixes

- Selecting a USB interface in Audio settings now causes recording to
  use it, without needing to also change the Windows default.
- A missing or unplugged configured device produces a visible OS
  notification instead of silent wrong-mic recording.

## What this does NOT change

- The audio capture, resample, and preprocess paths from v0.14.11 are
  unchanged. v0.14.11's restored linear-resampler path stays.
- The settings UI is unchanged — selection always persisted correctly,
  the bug was downstream of the dropdown.
