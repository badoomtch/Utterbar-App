# Utterbar 0.14.9 (beta)

The actual fix for "tinny / muffled" recordings on quality mics. Beta channel.

## What changed and why

Two related fixes in the audio capture path. Both came out of reading Handy's source (github.com/cjpais/Handy, MIT) and realising what we were doing differently.

**1. FFT-based resampler instead of linear interpolation.**

The previous `resample_f32` was a naive linear interpolator. Linear interpolation is the cheapest and worst resampler. It introduces aliasing distortion (no anti-aliasing low-pass filter), smears transients, and produces audible high-frequency loss. Going 48 kHz to 16 kHz through linear interpolation is exactly the "tinny, muffled, like a webcam" character users reported. The hardware delivered clean broadband audio; we destroyed it on the way down to 16 kHz before the recogniser ever saw it.

The new `StatefulResampler` in `services::audio::resample` wraps rubato's `FftFixedIn`, which does proper FFT-based resampling with built-in anti-aliasing. The rubato dependency was already in Cargo.toml; we just weren't using it. This is a one-time switch from "destroy the audio" to "transparent passthrough at any input rate".

The shape is taken from Handy's `FrameResampler`. Their version has been soaked across thousands of installs with the same cpal capture pipeline, so we lift the chunk-buffer pattern verbatim: cpal callbacks deliver variable-size chunks, the resampler buffers them up to a 1024-sample FFT window, processes, and emits.

**2. Picker respects the device's native rate.**

v0.14.7 tried to force 48 kHz to fix the tinny audio. That was the wrong fix and caused two regressions: U8 sample format errors (v0.14.8 patched), and fighting drivers that had reasons for their default rate. The proper fix was the resampler. With the resampler in place, taking the device's default rate (whatever Sound Control Panel reports) is the right thing — we resample cleanly to 16 kHz regardless of input rate.

The picker now follows Handy's pattern: read `default_input_config().sample_rate()`, then within all supported configs that cover that rate, pick the best decodable format (F32 > I16 > U16). No rate is forced. The "tinny on quality hardware" symptom is fixed at the resampler layer, not the picker layer.

## What this means in practice

If you have a Focusrite, Shure SM7, or any quality interface, recordings should sound like the actual mic again. The previous "laptop webcam" character is gone.

If you have a built-in laptop mic or a basic USB headset, things should sound the same as before — the linear-resampler artefacts were less audible at low input rates because there was less high-frequency content to alias in the first place.

The "audio capture stream opened" log line still tells you what rate and format the device delivered. After this update most quality devices will report 48 kHz F32; some report 44.1 or 96 kHz; none should be picking U8 or other undecodable formats.

## What's next

Things still on the parking lot from the Handy audit:
- Silero VAD for silence-trim during capture (faster transcribe, fewer hallucinations on quiet sections). v0.15+.
- Generic `build_stream::<T>` so we cover U8/I8/I32 for free. Currently the picker will simply error on devices that only expose those, which is rare; v0.15 polish.

## If something does go wrong

`%APPDATA%\Utterbar\logs\` has the app log. The new "audio capture stream opened" line tells us what rate / format the device delivered. Send the newest files to `hello@ddraig.dev` if the audio quality is still off.
